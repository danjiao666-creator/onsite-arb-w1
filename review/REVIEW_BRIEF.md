# 当前问题与请独立审阅的事项

## 目标与范围

目标是原任务期限内安全完成任务；不是停车越久越安全，也不是不计动态约束地尽快到达。请审阅原版 R43 及其最近两个独立原型，不把后续 201 版本或联合 MPC 的成败混入结论。

本次是失败现场交接，不是新版本验收。算法没有晋级，本地默认没有切换。以下数字来自已保存的运行，不是本次新测试。

## 已确认的卡点

### 1. +2.5 不是官方动力学上限

原平台与控制接口允许加速度范围为 -9.8 至 +9.8 m/s²。原 `candidates.py` 持续正加速度常量项为 +2.5；+4.5 / +9.8 是短脉冲，随后接 -9.8。滚动重选脉冲可能推迟原计划制动。因此问题不是简单把接口最大加速度改大，而是生成出的整段执行与选择依据是否一致。

A 轮改完整窗准入和 ETA 排序后，确实恢复了 68 / 332，说明推进选择值得修；但同时丢失 112 的原成功，峰速明显增大，不能直接接受。两个恢复结果不能抹掉，也不能只报净收益。

### 2. 路线、速度和占用时间没有被同时解决

分段多车道合流路线的曲率让原速度包络在后段降至约 14--16 m/s。主包络与部分恢复家族的约束应用不统一：旧常量项可给出乐观 ETA，执行速度却超包络。仅补统一速度门，112 仍超时。

整体合流路线加原模型速度序列后，68 / 332 起点模型 ETA 已能进入 10 秒预算，但原交通占用检查拒绝。对应 car4 / car7 的事后位置核对误差约 0.024 / 0.002 m，不能直接把这两个拒绝归为预测随意保守。该事后核对没有反馈给策略。

### 3. 最近原型从“起点有方案”走到“3.3 秒失解”

gap-event v2 保持原预测分支、道路、期限和控制模型，新增 actor-based before/after 方案。332 起点两项 ETA 为 9.475 / 9.627 秒，有限窗占用、道路和原速度包络通过；真实执行到 3.3 秒后，79 个候选中 77 个占用拒绝、2 个跟踪拒绝。

新冲突对象 car1 从后方变道接近。未提交 before / after 项分别预计在 +1.7 / +1.5 秒发生原预测占用冲突；同帧原 fallback 的 +9.8 脉冲也有 +2.4 秒 W1 接触预测。实验拒绝继续提交，实际轨迹止于 3.3 秒。这是算法中止，不是停车成功，也不是已观测碰撞。

三场共 230 个已提交步骤的下一状态与平台逐值一致；其中只有 332 的 33 步属于新增方案完整窗准入。112 / 68 的 197 个保留原策略周期没有因此获得新的完整窗认证。不能把首步执行对齐误读为后续始终存在可行解。

### 4. 事件名称没有成为硬约束

起点 before-car7 名义上要求 2.9 秒前到路径站点 81 m，但保存模型在该时刻没有兑现该目标。当前实现用目标速度反馈生成序列，最终选择检查没有硬验事件终端的站点/时刻满足。名为 before 不等于真的抢在车前，完整占用检查通过也没有认证事件承诺。

六秒 W1 与前两秒启用的 CV / 支持加速分支依原 R43 保留；六秒之外 ETA 尾段不含完整交通。有限窗合格并非全任务安全保证。

## 希望审阅者回答

1. **生成问题还是选择问题？** 原 R43 为什么会选中缺少剩余期限连接的方案？A 两恢复与 112 回归分别揭示了哪些必要条件，哪些只是排序效应？请指到代码或保存候选，不只建议换权重。
2. **能否给出更小、统一的规划表示？** 如果不再叠加脉冲、等待、before/after 模板，是否有合适的现有规划核心能表达车道、站点、时间、速度和实际执行记忆？替换哪一层，保留哪一层？
3. **如何让语义可核验？** 到站时间、车道占用时刻和期限应如何成为明确终端条件，而不是名称、参考速度或无交通 ETA？现有生成和核验需要共享哪些状态？
4. **如何避免滚动后丢解？** 332 在 3.3 秒出现 car1 冲突，早期方案是否已存在可识别的不可延续风险？需要完整反事实或可行见证；现有候选为空不证明物理无解。
5. **最小可证伪试验是什么？** 优先用 332 检验新表示能否形成真实闭环连接，再检查原成功 112；不先全栈重写或全 230 试跑。请给失败即停的判据，而不是承诺一个银弹。

## 待验证的方向，不是既定结论

上一轮讨论提出车道--时间--速度联合搜索或时空状态格作为候选方向；**尚未实现、没有验证收益，也不要求审阅者支持它**。如果提出新搜索器，需说明它与现有模板追加、更多采样的实质区别。审阅者可以否定该方向，但请说明现有证据支持哪种更小替换。

本轮不以放松 buffer、删除预测分支、改道路、延长期限、场景 ID 特判或未来真值作为解决方案。也不要求给出纸面上的绝对递归安全保证；需要明确现有保证的边界与可执行的验证路径。
