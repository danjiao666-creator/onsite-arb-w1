# R43 加速度、决策风格与任务目标诊断

## 结论

只看 GitHub R43 `1dbd0507353666c90ec7a9fdc3c752b62e85d001`，不使用联合 MPC 或后来 201 到达版本。

用户看到的保守/激进不一致有实现依据，但不能一概归为“变道意愿阈值不对”。主要问题是：两秒共同可行、六秒模型入框、软 ETA 预算和无解时的风险缓解使用不同排序；没有持续约束一次合流的可执行进展。有限候选与道路/跟踪门还会让正加速方案不能执行。

2.5 m/s² 是自家主候选与持续加速候选的设计上限，不是官方车辆的动力学上限，也不是自家执行控制器的统一硬限。只抬这个数，没有证据能解决上述问题。

## 1. 加速度到底限制在哪里

- 官方 `code/onsite-structured-test-3.1.5/utils/functions.py:129-130` 为加速度绝对值 9.8 m/s²、jerk 49 m/s³；冻结结果的控制器限值同样为 ±9.8。
- 冻结源码 `stack/core/arbiter.py:60-62` 的主候选第一段最高 +2.5、第二段最高 +1.5，切换点为两秒。
- `stack/core/candidates.py:21-40` 的恒加速恢复最高 +2.5；+4.5/+9.8 只提供 0.3/0.6/1.0 秒的短脉冲，随后接 -9.8。它没有一般性的“持续强加速完成合流”候选。
- 23 个超时中，21 个整场发出的最大加速度不超过 +2.5。另两个 `highway_merge_3_1_197`、`highway_merge_3_1_26` 发出过 +9.8，仍然超时。
- 4 个超时整场没有正加速度命令：`highway_merge_2_1_464`、`highway_merge_3_1_301`、`highway_merge_3_1_223`、`highway_merge_3_1_432`。这些场的命令最大为 -2.0；停车后的实际加速度可为零，不能混作命令。
- 17 个高速合流超时中，10 个首次正加速在 3 秒及以后，或全程没有正加速。

## 2. 为什么会一直“不敢走”

### 223：先制动，承诺的起步不断后移

在 `highway_merge_3_1_223` 的 5.0、7.0、9.0 秒，原记录都选择 `recovery:restart:-4:2`：先制动两秒，再用 +2.5 起步。此时实际速度已经为零，实际位置保持不动。3.2—9.9 秒连续选择带制动前缀的 restart 家族，而没有把之后的加速落实成当前命令。

这不是没有保留上一计划：生成器有 `continuation`，但它与每帧新生成、重新计时的 restart 一起竞争，旧计划的起步没有承诺。

同场 0 秒，所选 ETA 18.551 秒，超过原 10 秒期限，成本 49.799。正加速 +2.5 候选 ETA 7.218 秒，但成本 1275.987，其中车头时距项 1113.395、超期望速度项 152.825；超时预算是权重 3 的软惩罚，不能保证任务及时推进。该正加速候选道路未检查，不能据此称它安全可用。

同场 5 秒，+2.5 候选成本 42.471，已低于所选 48.758，预测占用也无冲突，却明确被 `mapped_road_body_outside` 拒绝。这里就不是成本压住了加速，而是现有路线/执行候选没有通过道路门。

因此，“有正加速候选没选”必须进一步区分：成本排序较后、道路未核验，还是道路已核验失败。不能都说成胆小。

### 301：重选横移位置，不等于真的左右变道

`highway_merge_3_1_301` 在 .50/.75/.95 的横移起点比例间重选，但最终横移锁定数为零；全程没有正加速，10 秒超时，末速为零，距目标约 254.390 米。可以确认横移未提交、进展丢失，不能说它实际反复变道又折返。

## 3. 为什么有时又看起来过于激进

### 正常分支：模型入框见证排在两秒后的预测无冲突之前

冻结 `stack/core/unified_evaluation.py:104-109` 的正常排序为：

1. 两秒占用前缀与跟踪合格，随后惰性检查两秒整车道路；
2. 优先有六秒模型内、原期限前的目标入框见证；
3. 再优先未来预测无冲突；
4. 最后比较成本。

`13_91_straight_in_opposite_left_96 @0.0s`：选 +2.5，两秒道路通过，但当前预测 2.8 秒车身接触、5.5 秒入框。同期 `main:13` 六秒占用预测无冲突，ETA 9.297 秒，小于 21.1 秒剩余期限，成本仅 9.787（所选 373.300），却没有六秒内入框见证。它的道路未核验，不能称完整安全替代；但排序确实优先了带较远预测冲突的入框见证。

这是推进目标与风险排序的直接证据，不是该场最终 11.2 秒碰撞的完整因果证明。该场动态横向分支关闭，也不能冒称它直接证明“变道太激进”。

### 风险分支：不是同一套任务成本继续优化

完全没有共同合格候选时，`unified_evaluation.py:180-187` 改为先延后预测接触/违反，再比较近期间隔等，成本在后。

`7_916_merge_921` 的原记录：

| 原时刻 | 模式 | 加速度命令 m/s² |
|---|---|---:|
| 31.7 秒 | 两秒共同合格 | -2.36 |
| 31.8 秒 | 无共同合格候选，风险缓解 | +2.5 |
| 31.9 秒 | 两秒共同合格 | +0.5 |

三帧转向命令完全相同，约 -0.044976 rad。视觉上的突然加速不代表新发起激进变道，而是可行性状态变化后换了裁判目标。不能仅凭加速度判断这个风险缓解动作比其他候选更危险。

## 4. 目标到底缺在哪里

R43 不是没有目标，而是没有把“原约束下持续可执行地完成合流，并尽早到达”贯穿整个过程：

- 两秒前缀通过不等于完整合流安全，也不等于下一帧还能延续。
- 六秒后接无交通尾部的 ETA 只是估计，不是可执行的到达保证。
- 超时主要靠软惩罚处理，不能阻止反复等待到期限耗尽。
- 横移起点逐帧选择，接近起点才锁定；`consistency` 只惩罚第一步纵向命令差，不保证机动连续性。
- 进入无共同合格候选状态后，目标切成短期风险缓解，与原先的到达排序不同。

下一步应该先统一任务、安全与持续进展的优先级，再分别定位预测走廊、候选覆盖、道路/跟踪可执行性。不是先统一“更激进”或单独放大 2.5；也不应将尚未完成道路核验的候选当作已被错过的安全机会。

## 审计范围与复核

本轮只有读取原源码、原 gzip 轨迹、已提取事件，以及汇总与校验；零新驾驶、零求解、零预测发行、零算法修改，未读 HOLD。

`objective_evidence.json` 保存 31 个终局失败的逐场摘要与关键候选快照，`summary.json` 为简表。`LATERAL_FINDINGS.md` 与 `lateral_evidence.json` 保存横向/模式切换细节。原始轨迹与冻结源码 SHA-256 保持，复核收据见 `verification.json`。

特别说明：道路采用惰性核验，未检查不等于失败或通过；`feasible_count=1` 是已找到见证的下界，不是精确可行候选总数。本轮没有证明改排序、抬加速度或保留某替代后整场一定成功。
