## 修复尝试回答了什么

### 1. 2.5 不是平台或控制器的正加速度上限

原候选族的持续正加速常量只有 +2.5；+4.5 / +9.8 是短时加速后接 -9.8 的脉冲，见 `source/stack/core/candidates.py:21` 和 `source/stack/core/candidates.py:31`。原平台/执行器可以给到 +9.8，本轮未改任何动力学限值，实际记录已经达到 +9.8。

68、332 原起点的 +2.5 候选确实能够通过完整窗检查。新选择去掉了内部超期望速度/时距成本跨越明显 ETA 差异压制推进的作用，两场真实恢复到达。原排序是原因之一，而不是唯一原因。

### 2. “所有可用方案中 ETA 最小”也不是正确的完整目标

68 场在 4.2 秒选 +9.8 脉冲，随后反复从新脉冲或递减的 continuation 中取首步；加速命令连续保持到 6.0 秒。不是 continuation 没有递减，也不是平台失配。候选每条都有制动尾部，但滚动重选可以反复延后尾部制动。

到 6.4 秒实际车速达到 50.487 m/s（181.75 km/h）。原 recovery 候选没有统一继承 main 家族的速度包络硬约束，原 `overspeed` 位于软成本；本轮 ETA 跨格优先后，软成本不能再阻止这一行为。完整窗道路/占用合格不等于合理速度或舒适合格。

| 场景 | 本地安全分 原→新 | 舒适分 原→新 | 交规代理分 原→新 |
|---|---:|---:|---:|
| 68 | 10.00 → 8.64 | 8.22 → 5.85 | 10.00 → 5.00 |
| 332 | 10.00 → 8.51 | 9.13 → 6.03 | 10.00 → 5.00 |
| 141 | 10.00 → 6.83 | 8.91 → 8.36 | 10.00 → 10.00 |
| 112 | 6.02 → 5.74 | 8.37 → 7.60 | 10.00 → 10.00 |

这些是 `bench/score.py` 的本地代理分，不是官方成绩。两场地图结果 `speed_limit=null`，代理分使用初速等规则推定限速，不能据此声称违反了一个已知法定限速。但实际高车速与大加减速有原始状态证据。

### 3. 112 的回归不是单纯“加速不够”

| 新轨迹时刻 | 已存证据 |
|---|---|
| 0.0 s | 从原滑行改为 +2.5，预计 ETA 8.109 → 6.587 s |
| 1.3 s | 同一新状态下原排序会选的方案，被新增完整窗门以 car5 / W1 的 2.4 秒后占用冲突否决；不是当前碰撞 |
| 2.6 s | 合格池 38 项，最大首命令也只有 -4.0；27 个正加速候选全部被预测占用拒绝 |

| 10.0 s | 超时，距框 25.113 m；原版 9.7 秒已经到达 |

最终锁定合流起点为 x=332.6108 m，原版是 x=228.8027 m；新版本的速度和路线选择共同把合流拖后了约 103.81 m。这个事实不能归因于“官方只给 2.5”。

同时必须保留另一面：原 112 自身有 28 个选中方案记录预测冲突，20 帧处于 risk mitigation。原到达不等于原版安全证书；不能为了恢复到达简单撤销新增占用检查或强持有旧路线。

本轮把完整窗准入和 ETA 排序作为同一个选择机制投入驾驶，因此未隔离二者各自造成多少回归。以上是保存状态中的门结果与真实轨迹链，不是已完成消融证明，也不是物理无解证明。
